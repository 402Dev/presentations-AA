Feature 01 / Form / Whole construction

The Component Registry

Construction-level feature: lists the components a construction needs before any word-order template is applied.

Category: Form
Central question
Which components must the construction contain before ordering begins?
Step 01
Inventory
Construction-level definition
The Component Registry is the construction-level inventory of the parts that must be present before any surface ordering rule is applied.
Step 02
Kinds
Two component kinds
Fixed anchor
A hardcoded word
Its lexical form stays fixed across instantiations, such as way, er, or ra.
Open slot
A variable blank
It accepts material constrained by labels such as Subject_NP, Object_NP, or Verb.
Step 03
Example
One compact example
Fixed anchor way
Open slots Subject_NP, Verb_Action, Poss_Pron, Obl_Path
This lists what must exist, not where each node appears in sequence.
Feature 01 / Examples + Utility

Same feature across constructions

English and Farsi are only the evidence. The stronger claim is that the same component inventory becomes reusable for comparison and structural query.

Two compact examples
English
The Way-Construction
[Subj_NP V_Action Poss_Pron way Obl_Path]
“He hacked his way through.”
Anchor way
Open slots Subject, Verb, Poss, Path
Farsi
Specific Accusative
[Subj_NP Obj_NP ra V_Trans]
“Ali ketab ra khund.”
Anchor ra
Open slots Subject, Object, Verb
Why this matters more than the examples
The real payoff is a reusable schema layer for the constructicon and for query.
Constructicon
Stable comparison unit
  • Store the component inventory once across variants and inherited templates.
  • Compare constructions by required parts before comparing surface order.
Query
Search by schema signature
  • Search for anchor and slot mixes before dealing with linearization.
  • Query the inventory first, then inspect how each construction realizes it.
components = 5 anchor = way | ra inventory before order

Decision prompt
Should Component Registry stay in the core form feature set?
Judge it by one practical standard: does it improve comparison and structural query, or does it only rename structure we already capture?
“Would we actually compare or query constructions through this schema layer?”

Feature 02 / Form / Slot level

The Topological Mapping Matrix

Slot-level feature: defines where each component slot may legally appear in the sequence, separating position from existence.

Category: Form
Central question
For each component slot, where may it appear in sequence?
Step 01
Map
Slot-level definition
The Topological Mapping Matrix assigns each component slot to legal zones or positions in the linear sequence, while leaving construction-wide slot existence to the Component Registry.
Step 02
Rigidity
Two slot-position logics
Absolute
Fixed position
The node occupies exactly one slot in the linear string. Scrambling this node is a grammatical violation.
Flex zone
Free inside a zone
The node can reorder relative to sibling nodes within its zone without violating the construction.
Step 03
Realize
One slot-level example
[Subj] [V] [Obj_Rec] [Obj_Thm]
The matrix stores legal positions: in English rigid indexing, each component slot is tied to a fixed place in the sequence.
Feature 02 / Examples + Utility

Position rules across constructions

English and Farsi are only the evidence. The stronger claim is that slot-level linear position can be modeled separately from component existence and queried across constructions.

Two compact examples
English
Rigid Indexing
[Subj V Obj_Rec Obj_Thm]
“She handed the reviewer the code.”
Zone logic Pre-verbal subject; verbal verb; two fixed post-verbal object slots
Rigidity All indexed positions are ABSOLUTE
Farsi
Terminal Anchoring
[Subj Obj_NP ra PP V_Trans]
“Ali ketab ra be man dad.”
Zone logic Subject, object, and indirect object share the preverbal field
Rigidity Preverbal field is FLEX_INTRA_ZONE; terminal verb is ABSOLUTE
Why this matters more than the examples
The real payoff is separating component existence from linear position.
Constructicon
Separation of concerns
  • Keep Component Registry and Topological Mapping distinct so legal word-order variation does not multiply schemas.
  • Store abstract templates once and let multiple constructions inherit the same topology.
Query
Topology-agnostic search
  • Search for ABSOLUTE or FLEX_INTRA_ZONE patterns independently of vocabulary.
  • Join constructions by topicalization or slot-rigidity patterns across languages.
rigidity = absolute | flex_intra_zone zone = preverbal | terminal position separate from existence
Feature 02 / Review
Decision prompt
Should Topological Mapping stay in the core form feature set?
Judge it by whether it captures lawful slot position independently of component existence, or whether it only restates surface templates we already know.
“Would we actually use this matrix to compare linearization patterns across constructions and languages?”
Use the note for one missing example, one topology query, or one reason the matrix still feels redundant.
